# Milestone 3: Backend Core & Persistence Implementation Documentation
**Author:** Nickyle Kannemeyer  
**Component:** `requests` Module, State Pattern, and Transactional Persistence  

## 1. Overview
This documentation covers the backend implementation for Milestone 3, comprising the 12 files committed to the repository. The implementation satisfies the core requirements for the Request Lifecycle by introducing the State Pattern for status transitions, atomic database transactions for history auditing, and Optimistic Concurrency Control (OCC) to prevent race conditions.

## 3. Core Component Implementation Details

### 3.1. Persistence Layer (`prisma/schema.prisma`)
The database schema uses Prisma ORM to map directly to our PostgreSQL database. 
* **Optimistic Concurrency Control (OCC):** The `ServiceRequest` model includes a `@default(1)` `version` integer field. Every time a request is updated, this version increments.
* **Integrity:** `RequestHistory` enforces a strict foreign key relationship to `ServiceRequest`, ensuring no history record can be orphaned.

### 3.2. The State Pattern (`statePattern.js`)
To remove sprawling conditional logic (e.g., `if (status === 'Open')`) and satisfy FR-007, the lifecycle is encapsulated into state classes.
* **Implementation:** An abstract/base `RequestState` class defines the `applyTransition(request, targetState)` contract.
* **Validation:** Concrete classes (`OpenState`, `InProgressState`, etc.) override this method to define their legal target states. If a user attempts to jump directly from `Open` to `Closed`, the current state object intercepts the request and throws an `InvalidTransitionError`.

### 3.3. Transactional Operations (`requestController.js`)
The controller and service layers work together to guarantee atomicity (ASR-3). When a staff member submits a PATCH request to change a status:
1. **Validation:** The State pattern validates the transition.
2. **Transaction Start:** A `prisma.$transaction` block is opened.
3. **Optimistic Check:** The `ServiceRequest` is updated *only* if the `WHERE id = ? AND version = ?` condition matches. If it fails, a 409 Conflict is returned.
4. **History Log:** The `RequestHistory` record (capturing the user ID, old status, and new status) is inserted.
5. **Commit:** The transaction commits both records atomically. If either fails, both roll back.

### 3.4. Automated Verification (`tests/statePattern.test.js`)
The Jest test suite focuses strictly on the request lifecycle business rules:
* **Positive Tests:** Simulates a request moving correctly through the lifecycle (`Open` -> `InProgress` -> `Resolved`).
* **Negative Tests:** Asserts that illegal transitions throw the expected validation errors to prevent the database from ever receiving a bad state.
